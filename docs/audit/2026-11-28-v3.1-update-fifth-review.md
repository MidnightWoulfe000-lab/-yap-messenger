# Fifth review of the v3.1 update

**Reviewer:** Codex, at the project owner's request.  
**Date:** 28 November 2026.  
**Revision:** HEAD `6d9fac4aead6280986160355365273b20a450742`, with the proposals and experiments as read. Input fingerprints and verification limits are below. The proposed update is not implemented.

**Verdict:** two High, nine Medium and one Low finding; no Critical finding. The ordered working-time calculation, separate recognition sending and matching keys, explicit attachment segmentation, terminal-hop simulator correction and revised size claims answer their earlier core defects. The design is still not complete enough to start building the integrated update. Catch-up session selection and its security cost, immediate recognition hiding, several admission rules and durable attachment progress still need decisions or corrections. Keep the implementation hold. Nothing in this report is approved for building.

**This is an AI-assisted review, not a professional security audit.** Text inspection, source inspection, arithmetic and executed model checks are distinguished below. No independent expert review, physical-radio validation or Android integration result is claimed. Suggested fixes ask for explicit contracts and tests; they do not invent cryptography.

## Findings

### 1. High — catch-up does not settle which session survives recovery

**Locations:** [group encryption](../proposals/group-encryption-v1.md) §3.2, lines 183–185, and §3.11, lines 550–577; §3.7 resynchronisation.

The retained bundle supplies a usable cryptographic starting point, which the former design lacked. The exchange now orders R to open a fresh session to S after S's stale setup failed. Section 3.2 separately says that when both members open sessions at once, the smaller identity is the initiator and the other session is dropped. There is no recovery exception or transition defining what happens to S's outstanding unusable session, R's new session, or any existing pending ciphertext.

Take S as the smaller identity. S has already opened a session using R's deleted monthly pre-key and has queued its setup. R cannot open it and initiates the proposed catch-up session in the opposite direction. An implementation applying the smaller-identity selection to these competing setups can discard the only usable recovery session. An implementation accepting R's session needs explicit replacement/archiving and retry rules. Neither the size experiment nor today's endpoint exercises this case. The text's unconditional “always opens” does not settle that state transition.

**Suggested fix:** specify session selection and installation for a failed stale setup followed by catch-up, for both identity orders and simultaneous recovery. State how authenticated recovery replaces or coexists with outstanding sessions and pending pieces, and how retries stop using the failed setup. Keep this within the pinned libsignal APIs and review the resulting state machine. Test lost replies, repeated hints and a restart at each installation boundary. Do not claim guaranteed end-to-end recovery from key availability alone.

### 2. Medium — the lifetime-key cost needs a narrower historical-confidentiality claim

**Locations:** group encryption §3.11, lines 579–582; §§3.6 and 4, erasure and protection of old ciphertext.

The text correctly admits that a later full-phone capture can open recorded catch-up setups, but dismisses this as adding little because the attacker already has live sessions and chats. That comparison omits material already deleted from those live stores. At minimum, the newly specified initial catch-up plaintext contains historical signed-bundle material and log heads. Retained setup secrets preserve access to that recorded material even if the corresponding live session and local records have since been erased. Today's live state is not equivalent to all historical setup plaintext.

Whether this also exposes a later sender-key hand-over depends on the exact sequence of messages and intervening Double Ratchet/SPQR progress. Step 2 does not itself carry a sender-key distribution message, and a fresh ratchet can prevent access to later traffic. This review has not demonstrated retrospective decryption of group chat from the retained pre-keys alone. Conversely, the proposal has not specified a payload restriction or demonstrated a boundary supporting its broad “adds little” assessment. The accepted policy needs a precise account of which historical material stays protected and which does not, especially beside §4's old-ciphertext claim.

**Suggested fix:** document the permitted initial catch-up payload and the historical material recoverable after capture, and qualify the confidentiality claims accordingly. Have the owner assess that cost and obtain the separate cryptographic composition review already called for. Add a pinned-library experiment covering recorded setup traffic, subsequent hand-overs, intervening ratchets, key/history deletion and later capture of retained catch-up secrets. Report what remains readable rather than assuming either complete historical exposure or complete protection. Do not substitute a new construction in implementation.

### 3. High — an immediate hide can reopen links with the old sending keys

**Locations:** [mesh](../proposals/local-mesh-v3.1-group-envelopes.md) §3.3, lines 637–650; §3.9, lines 766–768.

The two-table solution fixes the earlier contradiction. Its publication order does not yet enforce “hiding takes effect at once”. Hiding closes links and opens new ones under a new link ID immediately; rebuilding the table happens in the background. If a new link starts before that rebuild is published, it can capture the old table and send a genuine recognition tag to the very friend being hidden from. Whole-table swapping does not by itself prevent this race. The same gap affects deletion, and a week-boundary link can capture an obsolete sending epoch.

This is particularly material where a friend's phone has been taken: disclosure on the first new link defeats the intended immediate action. A local direct-transfer switch can block file transfer but does not retract a tag already sent.

**Suggested fix:** define the ordering between switch changes, invalidation, queued work, table publication and permission to probe on new links. During the gap, specify safe bounded behaviour that cannot emit the withdrawn tag. Check local hiding again before a direct handshake/transfer starts. Test with the table worker deliberately stalled, a queued probe, an immediate reconnect and contact deletion. Keep incoming matching material available as intended.

### 4. Medium — lifetime replay state and failed-setup work have no complete resource contract

**Locations:** group encryption §§3.2/3.11; [storage](../proposals/local-storage-v1.md) §§3/5; [current pre-key adapter](../../endpoint/src/store.rs), `Records::mark_kyber_pre_key_used`.

Monthly pre-key retirement formerly supplied a lifetime bound for used-base-key records. Catch-up pre-keys now persist for the whole membership, and their used-base-key records must persist just as long. A rate bounds growth per day, not across an arbitrarily long membership. There is no saturation/admission rule for this non-prunable state or explanation of its share/reserve accounting. At the existing four-setups-per-member-per-day ceiling, 127 peers can still add 508 records daily in one group; rates alone do not bound the table's lifetime size.

The new one-answer-per-claimed-sender/hour and ten-answer/hour limits are useful, but bound outgoing answers. The text does not say whether repeated failing attempts debit the existing four-per-day pre-PQ-work budget, when that check runs, or how much failed setup work may precede it. A former member can name a current member using known fallback material. If unauthenticated hints consume all recovery allowances, honest catch-up can be suppressed; if failures do not consume a work allowance, the answer rate does not bound decrypt work. Ordinary flooding limits still apply, but do not answer this particular admission choice.

Today's Yap adapter removes the Kyber pre-key on use; it is not a reusable last-resort implementation. The pinned libsignal in-memory adapter instead retains the key and records `(Kyber ID, signed-pre-key ID, base key)` reuse. Neither is durable evidence for the proposed lifetime store.

**Suggested fix:** specify bounded failed-attempt work, reply scheduling, durable replay-record accounting and behaviour when that state cannot grow. Preserve replay refusal when records cannot be retained; do not silently evict them while retaining the reusable private key. Explain the resulting availability limits. Test repeated failed hints, valid distinct catch-up setups, exact replay after session loss and restart, and replay-store exhaustion.

### 5. Medium — resumed discovery still depends on an unspecified current-QR lookup

**Locations:** [pairing](../proposals/encrypted-pairing.md) §2, lines 99–109; §3, lines 146–176; storage §3 `pairing`.

The stored resume state and deadline are genuine answers to round four. However, a `PAIR_FIND` is answered only if it matches the receiver's “own current QR” for an attempt it also scanned. After Ready or restart, the phone may have no displayed/current QR, or may have opened a fresh attempt. The saved resume fields contain “the commitment”, without distinguishing the peer commitment sent in discovery from the local commitment needed to receive discovery. The handshake acceptance exception for an attempt in its resume window does not specify how an incoming anonymous handshake is dispatched to that saved attempt.

An implementer still has to choose whether reopening a QR invalidates the old lookup, which commitments survive, how original handshake versus resume is selected and how many candidate PSKs/work items an unsolicited frame may cause. Moving the queue after successful authentication is correct; stale-link queued or in-flight sends also need an explicit cancellation/handoff boundary.

**Suggested fix:** define separate bounded lookup and admission rules for a displayed QR and a retained resumable attempt, retain the local and remote discovery values actually required, and state replacement/cancellation behaviour. Give canonical frame lengths and dispatch context without exposing permanent identity. Test Ready restart with no QR open, a new QR opened during an old window, stale-link queued packets and simultaneous resume links. Keep the ten-minute retention independent of UI Ready.

### 6. Medium — pair-wide friend requests still have group-bound signatures and an undefined deadline basis

**Locations:** pairing §5, lines 182–248; storage §3 `friend_requests`.

The smaller-identity winner resolves the former crossed-secret defect. The new pair-wide rule is not reconciled with the signed group binding: step 1 signs the group ID explicitly so the request cannot move to another group, while “several shared groups” says the same request through another group gets the cached accept. It does not choose whether this means new signed transport wrappers for the same immutable pair request, a refusal to change routes, or some other representation. Departure before Ready is likewise ambiguous when another shared group remains available.

The request fields contain no creation time, expiry or agreed age/deadline. “Seven days from the request” therefore has no common wire basis. A request first delivered near A's deadline can give B a fresh seven-day local window. Retaining only request IDs for 30 days does not by itself reject a much later replay, particularly after contact deletion; the text promises old requests are ignored without stating the retention limit on that promise. Cached accepts are described in the response as retained with the tombstone, but that retention rule is not stated explicitly in §5.

There is also no explicit bootstrap retry/cache rule for this seven-day route: step 4 retries only until an accept arrives. Importing §3 wholesale would bring a ten-minute QR/Noise resume window that this route does not use. Today's endpoint caches kind 03's reply and retries under its current envelope/contact lifetimes; that is not an implementation of a seven-day group-carried handshake.

**Suggested fix:** specify immutable request/accept bindings, the authorised group route or routes, the signed deadline/age rule and its clock checks, exact cached-response lifetime, and bootstrap retry/cancellation through local Ready. Define late replay after tombstone expiry and loss of group authorisation. Test crossed requests in different groups, group departure, delayed first delivery, lost kind 04 and restarts. Retain the separate contact session and contact-slot admission.

### 7. Medium — incremental reclamation still conflicts with full VACUUM and the physical floor

**Locations:** storage §5, lines 175–187; §7, lines 241–242; group encryption §3.6 erasure.

Section 5 chooses `auto_vacuum = INCREMENTAL` and says compaction never needs a second database copy. Section 7 still explicitly orders `VACUUM` after large deletions. These are different operations. Incremental mode needs explicit incremental-vacuum calls; setting the mode alone does not perform them. Full `VACUUM` rebuilds through a temporary database and can need free space up to twice the original database's size. The fixed 256 MB headroom is not a budget for rebuilding a database approaching the 2 GB logical limit. See [SQLite's incremental-mode rules](https://www.sqlite.org/pragma.html#pragma_auto_vacuum) and [VACUUM's space requirements](https://www.sqlite.org/lang_vacuum.html).

The new before-write free-space check is useful, but neither bounds an operation's physical growth nor defines which writes may consume the 256 MB once below the ordinary threshold. A post-commit checkpoint at 16 MB is a trigger, not a hard WAL bound or a stated response to a blocked/failed checkpoint. Short screen reads reduce one cause of blockage; they do not define all readers or failed reclamation. The carrier and endpoint also draw on the same physical headroom.

**Suggested fix:** choose the actual reclamation calls and bounded work schedule, reconcile the erasure wording, and define transaction/chunk growth admission and shared headroom use. State failed-checkpoint, failed-commit and low-space cleanup behaviour. Test another app consuming disk, both stores writing, blocked readers and deletion at the floor. No fixed floor can guarantee progress if another app consumes all physical space; scope the promise accordingly.

### 8. Medium — essentials still cannot pass an exhausted ordinary rate gate

**Locations:** storage §5, lines 188–205; mesh §1.3 ACK semantics.

The reserve rule says every envelope first passes the ordinary per-sender rate and only after authenticated decryption can essentials use their separate allowance. If a contact has already sent 1,000 ordinary messages this hour, its next receipt is refused before it can be classified. The same applies to an urgently needed key change after that sender exhausts the ordinary budget. This contradicts both “shrinking operations are always allowed” and the test promising receipts/key changes still go through while a contact floods. Merely reserving bytes cannot open a closed admission gate. It is also unclear whether essentials share the 3,000/hour global gate or have a separate phone-wide work bound.

Low-space order has the same classification issue: if incoming envelopes are refused before authenticated classification, their essential contents cannot use the reserve. If they are provisionally handled for classification, the work and durable-state boundary must be stated. Separately, an already committed mesh ACK means handled, not end-to-end acceptance; a later endpoint refusal cannot promise that no earlier hop acknowledged the envelope.

**Suggested fix:** define one bounded admission sequence for unclassified input, authentication, ordinary/essential classification and commit, with explicit per-sender and global work limits. State which acknowledgement is withheld at each rejection point. Test a receipt and justified key change immediately after exhausting ordinary rates, and again with logical storage full and physical space low. Avoid an unlimited decrypt path in the name of essential traffic.

### 9. Medium — rolling fair shares do not define service for whole offers

**Locations:** mesh §1.4, lines 351–379 and `WANT` format.

The settled-list cap is a concrete improvement. The new fairness claim still lacks an implementable allocation rule. Answers are whole offers of up to 64 entries; busy status answers none. With twelve active links the nominal share is 50 entries. An untouched 64-entry offer cannot fit that share. The text does not choose partial answers, smaller retries, credit carried across time, or controlled borrowing. “Unused share goes to whoever asks next” can permit progress, but without a defined release point/reservation for waiting links it can also let a fast link take the allowance just before a slower link retries. A continuously rolling minute has no single end at which unused shares become available.

Link arrival/expiry also changes shares after some links have already spent their allowance. This need not invalidate copy accounting, but it does invalidate the unconditional “no link can be starved” claim.

**Suggested fix:** define entry/page granularity, share recalculation, unused-share release and retry/service ordering, or narrow the guarantee to best-effort progress. Test twelve 64-entry offers, changing active links and one aggressive link against a slow retrying link. Preserve busy status and bounded settled/seen state. After cache eviction, repeated traffic may be more than one extra offer if the receiving phone has also forgotten its seen state; describe that as a bounded-cache trade-off rather than an absolute once-only cost.

### 10. Medium — current-label batch cleanup assumes encryption the container does not have

**Locations:** group encryption §3.11, lines 622–661; mesh §§1.3/1.5.

A valid `YGB1` batch is a directory followed by independently wrapped pieces. It is not one sender-key-encrypted group message. Yet the current-group-label path says to keep it without opening, then delete it if it fails decryption “under that sender's key” in step 7. Applying that literally to a legitimate batch deletes it, because no such whole-batch decryption exists. Even interpreting it as the member's own piece is wrong when the member has no piece in this smaller retry batch, or its inner piece is bad while another recipient's is good. The following rule expressly says individual inner failures leave carried bytes unchanged.

The 32-decryption rule needs a precise scope too. It bounds directory-only admission, then step 7 says to open each found piece. A crafted directory can contain many labels for this phone, including repeated labels; no uniqueness rule is stated. Reopening the admission piece and opening every other match can exceed 32 total outer attempts. If the intention is only a pre-ACK bound, state the separate worker bound and scheduling. Exhaustion after one successful opening also needs an explicit retention result rather than the ambiguous “past 32 ... not for this phone”.

**Suggested fix:** distinguish ordinary group ciphertext from batch containers before applying post-ACK validation/deletion. Specify batch retention independently of installation of one member's inner piece, cache successful outer openings or account for reopening, and define total per-envelope work and exhaustion behaviour. Add the valid-outer/invalid-inner, later collision-key, no-own-piece current-label batch and 33-candidate tests. The corrected outer/inner ACK order itself should remain.

### 11. Medium — saved attachment ranges are not ordered with durable file writes

**Locations:** [attachments](../proposals/attachments-v1.md) §§2–4, especially lines 84–94, 132–134 and 178–181; storage §7a.

The new rule correctly recreates a missing staging file and resets its ranges. It misses the case where the file exists but a range was committed before its bytes reached durable storage. After a crash, the receiver can advertise that range as present even though it is absent or contains old bytes. The sender then omits it. The final authenticated hash prevents showing corrupt content, but does not repair progress: the rule deletes a failed staging file without stating the same-run range/reservation reset and retry transition.

Storage §7a gives sync/rename/commit order for adding a finished file, not for repeated writes to an existing staging file. Its startup rule also shows a missing referenced file as “Attachment missing”, whereas the attachment proposal recreates one for accepted incomplete manifests. Implementations need an explicit incomplete/validated/published/deleting distinction to select the right recovery rule. An accepted manifest does not necessarily mean an incomplete transfer: recounting reservations from all accepted manifests must avoid charging completed files twice.

The exact STREAM cut is now clear, but authenticated manifests must be checked for the equations linking plaintext size, count and encrypted size before staging/range allocation, with checked arithmetic. Range-count/frame-work bounds remain unwritten for direct transfers; arbitrary tiny chunks can create far more bookkeeping than a file-size reservation covers.

**Suggested fix:** define the write/sync/range-commit order, range acknowledgement boundary, transfer states and idempotent reconciliation for existing as well as missing files. State hash-failure retry/reset and reservation release/publication accounting. Bound/coalesce range metadata and validate all manifest relationships before admission. Test power loss after each chunk-write/range-commit boundary, partial files with recorded ranges, failed final validation, publication and deletion. Keep full hash and segment validation as the finish line.

### 12. Low — some tests and summaries still contradict the revised lifecycle

**Locations:** pairing risks/test plan; labels §1/test plan; mesh §§1.4/1.8 and Part 1 tests; storage test plan.

Pairing risk 6 still erases discovery on completion; the substantive rule now retains it to the resume deadline. Its test plan still says a restart before Ready cancels, despite Confirmed attempts surviving restart, and says both phones fail after the deadline despite the Ready exception. Labels' test still says a link closing before completion cancels. Mesh's tests promise a settled envelope is never offered again for that link, despite the new 20,000-key eviction exception, and §1.8 still says a removal costs at most five stamps per member despite the six-batch measured case.

The SQLCipher test still says a changed page fails to open the database. Page authentication is checked when a page is read, so opening alone is not a whole-file check; this was already noted in round four and accepted as outstanding in the response. See [SQLCipher's page authentication design](https://www.zetetic.net/sqlcipher/design/). The response is useful context but cannot override conflicting acceptance tests left in the implementation input.

**Suggested fix:** reconcile these tests and summaries with the chosen lifecycle and cap rules; name a deliberate integrity check if whole-file verification is intended. These are documentation corrections, separate from the substantive transition problems above.

## Clock, recognition, attachment and size assessments

The ordered clock rule answers the original arithmetic counterexample: after accepting T+36 hours, the next base begins at that accepted value, so a wall-clock correction cannot return it to T. Taking the later durable value across stores also answers a crash between their successful commits, provided both are opened and reconciled before expiry, label generation or carrier pruning. Today's `EndpointRepository.kt::now()` and `core/src/relay.rs::normalize_clock()` retain a high-water anchor, but still implement separate clocks without the proposed confirmation gate or SQLCipher reconciliation. That is source context, not evidence that §8 is built.

The shared-clock implementation still needs one serialised authority, defined startup/commit ordering, overflow handling and failure behaviour when a store is unreadable. Persisting “with the next commit” guarantees a durable floor for committed changes; it cannot literally preserve every uncommitted value returned immediately before power loss. Scope that sentence accordingly. Recreating a carrier store must not reset the endpoint's surviving floor. Restored copies of both stores and mistaken forward confirmation remain accepted open limits. Re-pairing contacts does not itself lower a global working-time floor; the prompt must not imply it repairs the phone's clock. These points require explicit handling and tests, but do not reinstate the previous in-run reversal finding.

Separate sending and matching tables now support A-hidden/B-visible, A-visible/B-hidden, both-visible and both-hidden at the key level. Checking previous/current/next weeks handles ordinary boundary skew when those secrets exist. Fixed HMAC counts alone still do not prove equal whole-exchange timing: filler replacement, shuffling, background publication, cap handling, queue cancellation and selection require measurement. The response correctly calls these unmeasured. Finding 3 concerns an explicit privacy race, not an inferred timing measurement.

Attachment segmentation now has one coherent interpretation. Independent arithmetic checks give:

| 0 | 1 | 16 |
| 1 | 1 | 17 |
| 65,535 | 1 | 65,551 |

The final flag is correctly an authenticated nonce input selected from the manifest, not an extra byte read from the file. This is arithmetic/text verification, not a STREAM interoperability test. Numeric image/thumbnail/audio limits and memory-only pre-manifest pieces answer the former omissions. Decoder-header parsing and resource limits still need implementation tests. The direct channel still lacks the canonical week-bearing initial message, PSK-info/prologue bytes, bounded dispatch/error states and FILE message/range encodings identified in the fourth review and explicitly left open in the response. Complete Noise messages must respect the 65,535-byte limit including authentication overhead. No channel/decoder implementation exists here to verify.

The size program still includes the new 32-byte inbox field. Its counted overhead is 72 bytes per piece, plus a five-byte batch prefix. For the documented new-session/16-event sample, 126 × 2,582 = 325,332 bytes exceeds five × 57,344 = 286,720, so at least six batches per sender and 127 × 6 = 762 envelopes are necessary. The revised text acknowledges fallback copies and retries are additional. The program does not execute an outer wrapper, batch parser, replay, session-loss recovery or persistent pre-key store; `Pair::send()` encrypts a fresh message on each call. The revised attribution is accurate. Actual encoded-size admission is necessary even if the sample is reproduced.
