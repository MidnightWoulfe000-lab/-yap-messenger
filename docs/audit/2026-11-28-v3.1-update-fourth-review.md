**Verdict:** four High, seven Medium and one Low finding; no Critical finding. Reservation at OFFER, a distinct busy WANT, full settled keys, the complete-heads group-state fallback and the revised envelope bounds answer their original contradictions. SQLCipher for both stores, attachment reservations and an explicit pairing finish line are substantial improvements. **This is an AI-assisted review, not a professional security audit.** Proposal inspection, source inspection, arithmetic checks and executed model checks are distinguished below. No independent expert review, Android integration test or physical-radio validation is claimed.

## Findings

### 1. High — a permanent fallback address does not supply a usable recovery session

**Locations:** [group encryption](../proposals/group-encryption-v1.md) §§3.2, 3.7, 3.11; [labels](../proposals/rotating-address-labels.md) §7.

Keeping the fallback inbox for the membership answers address expiry. It does not answer the inner-session problem. R receives S's setup message encrypted to an already deleted pre-key. Section 3.11 says R sends a catch-up piece containing its current log heads, allowing S to fetch a new bundle. But every such piece must itself contain a one-to-one libsignal message. If R also has only S's expired bundle and neither retains a usable session, R cannot construct an answer S can read. Log heads are pointers, not the missing log/bundle transport.

The proposal acknowledges this exact two-sided case and asks for re-invitation, so it is not concealing the limitation. However, “however long ago” and “there is no time limit on being away” overstate the resulting recovery guarantee. An old but still-active membership can require a new admission. The rule also does not define how a failed, unauthenticated setup authorises a reply: a known inbox key establishes group knowledge, not the claimed sender's identity. A removed member retains those fallback keys and can manufacture apparently stale setups naming active members, consuming recovery work unless this path is bounded.

**Suggested fix:** state the address guarantee separately from the conditions for end-to-end recovery. Specify the complete stale-bundle exchange, including how current signed bundles/log data become available, authentication, rate/work bounds and the exact re-invitation behaviour when no route works. Review the proposed long-lived last-resort pre-key trade-off separately; retaining it is not authorised by this review. Test both sides losing sessions and replacing bundles during a long partition, not just both sides missing inbox rotations.

The accepted privacy cost also needs a narrower description: a removed member can recognise S-to-R fallback traffic across hours whenever it knows the relevant membership keys. Last-copy broadcasting prevents inferring R's location merely from the address, but does not make this traffic unlinkable or remove the already acknowledged possession/re-offering observations. Do not promise that the observer cannot “follow anyone with it”.

### 2. High — the written working-time formula can move backwards within one run

**Locations:** [local storage](../proposals/local-storage-v1.md) §8; labels §1. Code: `EndpointRepository.kt::now()`, `core/src/relay.rs::normalize_clock()`.

Rule 1 takes the later of wall time and **saved working time at start + elapsed since start**. Suppose the app starts at T, wall time advances by 36 hours, and an operation accepts that advance under rule 2. Without restarting the app, the user corrects wall time back. The original start anchor plus a few seconds is now lower than the accepted T+36 hours; the formula returns to it. Saving the high value in `meta` does not change the stated anchor “at start”. A confirmed larger jump has the same defect unless confirmation explicitly resets the anchor.

This violates the owner rule and can reuse earlier label/key epochs or change expiry decisions after irreversible pruning. Today's Kotlin code instead includes the previous effective time plus each elapsed delta; the carrier similarly updates its clock anchor on every normalisation. Those implementations demonstrate the missing high-water step, although neither implements the proposed two-day confirmation policy.

**Suggested fix:** write one ordered clock transition using the latest effective value and elapsed delta, then apply the wall-clock candidate and confirmation gate before returning or committing time. Define confirmation/rejection, resume/reboot, and how the second database obtains the same committed floor. Test a sub-two-day advance followed by correction in the same process, confirmed/rejected larger jumps, restart and crash between the stores' commits.

The removal of contact-controlled advancement is an answer to the previous attack. The new threshold is an owner choice, not a cryptographic clock guarantee: an accepted advance of up to two days can already expire all 24-hour mail. A wrongly confirmed larger advance remains irreversible under “never back”. Document that consequence and the unresolved recovery procedure beside the prompt.

### 3. High — pairing discovery and a Ready responder's retry lifetime remain inconsistent

**Locations:** [encrypted pairing](../proposals/encrypted-pairing.md) §§2–3, risk 6 and tests; labels §§1–2, 6; storage §3 `pairing`. Code: `SecureModel.kt::requestBundle()`, `engine.rs::receive()` kinds 03/04.

Section 2 first requires today's cleartext BUNDLE_REQUEST to find the link, then says today's cleartext BUNDLE_REQUEST, BUNDLE and confirmation frames are removed. No replacement discovery frame is defined. Today's code really broadcasts the scanned bundle commitment in type 7; removing its handler while requiring that exchange prevents the new handshake from finding its intended link. Removing cleartext sensitive payloads is necessary, but does not itself replace discovery.

The new Ready boundary correctly matches today's asymmetric bootstrap. Yet after the responder accepts kind 03 and its kind 04 is lost, the initiator must resume. PAIR_HANDSHAKE is accepted only with an attempt in progress, storage retains attempts only in Confirmed state, and risk 6 says the discovery value is erased on completion. The Ready row says “Nothing to do”, while the restart rule keeps only the responder's contact. There is no explicit retention/reconstruction contract for the responder's PSK, QR transcript, attempt lookup and cached ACK through the remaining ten-minute retry window, including a restart after Ready. Showing “Finishing pairing” does not supply those credentials. Erasing them at local Ready breaks the promised retry.

Labels §2 and the end of pairing §3 also still bind the queue to “that one link”, although resume explicitly permits a different local link. The resume prologue is given only as a fixed string, with no canonical attempt/peer/link binding stated. The PSK is attempt-derived, but that does not document the complete resumed channel context or local dispatch rules.

**Suggested fix:** specify which discovery frame survives, its version and attempt-scoped admission, then define the responder's post-Ready retry state and erasure deadline independently of the contact's UI state. State which data survive a Ready restart, how the original initiator/responder roles are preserved, and how a queue is rebound after a fresh authenticated resume handshake. Reconcile every labels/storage description and test loss of kind 04 followed by responder restart. The disclosed one-side-Ready outcome may remain an accepted distributed-completion limit; it need not be falsely presented as preventable.

### 4. High — crossed group friend requests can leave different pair secrets installed

**Locations:** encrypted pairing §5; storage §3 `friend_requests`; group encryption §§3.2, 3.11.

Let A request B with secret a while B requests A with secret b. B accepts A's request and saves a; A accepts B's request and saves b. A then receives the accept for its own request and saves a; B receives its accept and saves b. Both followed the five steps, yet their contacts now derive different labels and recognition keys. Selecting the smaller identity to initiate the new libsignal session does not select which request's pair secret or week wins.

There is also no finish/cancellation contract for this route. B's accept is retried only in response to A's request; what happens if the deadline arrives after B accepted but before A receives it? There is no stated handling for a delayed accept after expiry, a request repeated after friendship/contact deletion, or leaving/removal from the group while bootstrap is still confined to group pieces. A completed friendship surviving departure is clear; an incomplete one has no equivalent to §3's cleanup and completion states. The five outgoing-request limit does not bound incoming retained requests/cached accepts across groups.

**Suggested fix:** define one canonical active request per identity pair, deterministic handling of crossed requests and multiple shared groups, immutable request/accept bindings, contact-slot admission and a complete local state machine through bootstrap. Specify cached-response retention, replay after deletion, expired accepts and loss of group authorisation before Ready. Preserve the separate contact session and the “not checked in person” distinction. These are protocol/state decisions to review, not details an implementer should guess.

### 5. Medium — logical byte counters do not yet enforce the physical reserve

**Locations:** local storage §§2–5, 7–7a; attachments §4.

The new counters and admission reservations address the previous unbounded allocation problem. But counts of record sizes are not physical SQLCipher database/WAL sizes. An update or deletion can need new WAL pages, indexes and temporary space; long-lived read transactions can delay reclamation. Checking real file sizes at start does not enforce the “last 1 GB” floor during a long-running carrier or attachment transfer. “Keeps room for compaction” gives no amount or admission calculation. A nominal 64 MB logical reserve is not a guarantee a receipt/deletion transaction can physically commit.

The rate rule refuses envelopes above 1,000/hour per sender or 3,000/hour globally, whereas shrinking operations are “always allowed”. It does not say how authenticated state-reducing controls are classified/admitted without making the control reserve an unlimited work path. Historical “other chats keep working” requirements therefore still need overload semantics, not just higher capacities.

Both databases being encrypted is coherent with the seized-file goal. The carrier nevertheless receives only “its own random key wrapped the same way”; exact carrier wrapper/Keystore names, partial first creation, missing-key recovery, erase/upgrade order and shared-time startup reconciliation are not specified alongside the endpoint's four cases. Do not implement the second key by copying the first database's wrapper path.

**Suggested fix:** specify physical headroom accounting and checks during writes, WAL/checkpoint/read-transaction bounds, compaction headroom and low-space failure behaviour. Define control admission and bounded work separately from ordinary messages. Give both stores explicit key/file lifecycles and restart reconciliation. Test reserve exhaustion, failed commits, long readers and disk space consumed by another app. The values can remain provisional; the enforcement algorithm cannot.

### 6. Medium — settled-state capacity and busy-WANT fairness are still promises without rules

**Locations:** [mesh v3.1](../proposals/local-mesh-v3.1-group-envelopes.md) §1.4 “Paging”, “Budget” and reservation lifecycle.

The full-key fix is correct, but a long-lived link can settle more than 10,000 envelopes while the 10,000-entry store turns over. The per-link list is memory only and promises never to offer a settled envelope again on that link. No full-list action is defined: unbounded growth, deleting old settled keys, refusing fresh work and closing the link have different consequences. The 200,000-entry dropped-last-copy table likewise needs an admission/eviction action at its cap. Current-store capacity is not a bound on encounters over a link's lifetime.

The distinct busy status answers the original empty-WANT contradiction. However, “a link that keeps getting busy answers still gets its turn once the minute rolls on” does not follow from a shared rolling 600-entry budget and retry delays. Other links can repeatedly consume the next allowance before this link retries. There is no scheduled turn, per-link share or persistent pending-answer queue establishing that claim. This is an availability limitation under contention, even when copy accounting remains conservative.

**Suggested fix:** state bounded-state saturation behaviour and the associated once-per-link guarantee precisely. Define the fairness mechanism or withdraw guaranteed turns under competing load. Include store turnover beyond 10,000 distinct keys, exhausted seen state, long-lived links, busy retries across window boundaries and eviction of an envelope with outstanding offers. Keep reservation-at-OFFER and conservative crash spending; neither needs a new cryptographic mechanism.

### 7. Medium — batch retention requires decryption before the allegedly pre-decryption ACK

**Locations:** mesh §§1.3, 1.5; group encryption §3.11 batch rules.

Mesh §1.3 still places ACK after the store/drop decision “before any decryption”. Group §3.11 now makes a piece count as “for me” only after its outer AEAD opens, specifically to prevent copied-label retention. A stale member deciding whether to keep a last-copy batch must therefore decrypt at least one outer layer before that decision and ACK. Implementing the mesh sequence retains the old marker attack; implementing the group sequence violates the stated ACK timing/order contract. A matching current group destination also needs a stated validation path rather than an implicit exception.

The corrected ACK meaning, “handled”, is appropriate. No measured timing equality is claimed, and that is also appropriate. This finding concerns contradictory required ordering, not a newly measured side channel.

**Suggested fix:** publish one receive sequence distinguishing bounded outer authentication, inner libsignal processing, durable carrier/seen-state commit, ACK and generation-install acknowledgement. Say explicitly which work may precede mesh ACK and which errors keep/drop the batch. Account for collisions: up to four key candidates per matching label does not automatically equal the stated “one AEAD decryption per match”. Test an invalid copied label, a valid outer layer with invalid inner content and a collision candidate that opens only on a later key.

### 8. Medium — the hidden-contact table prevents the recognition hiding is meant to preserve

**Locations:** mesh §§3.3, 3.9.

The fixed table substitutes random throwaway keys whenever recognition is hidden, and both probe generation and checking use that table. Section 3.9 nevertheless says a hidden phone still recognises friends who have not hidden. If A's hidden slot contains only random keys, A cannot match B's genuine tag. If A retains the real key in that same slot to recognise B, using it for generation would advertise the tag A intended to hide.

**Suggested fix:** distinguish outgoing tag eligibility from incoming matching material in the cached table and specify fixed-work selection for each operation. Define atomic invalidation/rebuild when a contact is removed or hidden, including links reopening immediately after ID rotation. Test all four combinations of A/B hiding and verify that direct transfers never start when either local switch prohibits them. Full-operation timing, filler replacement/shuffling and queue cancellation still require measurement and explicit scheduling; the fixed HMAC count alone does not establish the required privacy property.

### 9. Medium — attachment boundary and staging rules still permit incompatible implementations

**Locations:** [attachments](../proposals/attachments-v1.md) §§1–2, 4, 6; storage §7a.

StreamBE32's named nonce construction and manifest checks answer most of the previous format finding. The text still requires the last plaintext segment to be “shorter” and each encrypted segment to be 64 KiB+16. It does not choose between a full-sized final segment and an extra empty final segment for an exact multiple of 64 KiB, nor define an empty file. Both choices affect count, hash and size. The library's final flag is part of nonce construction, not an extra serialized flag a receiver can simply read. The receiver must know which segment is final from the canonical lengths/count and authenticate it with that flag. [RustCrypto's StreamBE32 documentation](https://docs.rs/aead-stream/latest/aead_stream/struct.StreamBE32.html) describes the counter and final-block flag; it does not supply Yap's file termination convention.

Section 2 calls 256 KB the prepared-file ceiling; §6 calls 262,144 bytes the **encrypted-file** ceiling. A 262,144-byte plaintext in four segments needs at least another 64 bytes of tags. The same distinction affects the 100 MB ceiling. Make the ciphertext limit authoritative before accepting a manifest.

Section 2 says pre-manifest pieces are dropped but also wait for ten minutes, with a count bound. Section 4 prohibits any write without a full-size manifest reservation. State whether those orphan pieces wait in bounded memory or consume staging space, and how their untrusted total/sender scope is checked. Crash cleanup also says to remove a reservation with no staging file; a newly accepted manifest legitimately has no file yet, so its durable history/manifest must be reconciled or re-admitted rather than left permanently unable to receive chunks. Decoder “pixel limits” other than outgoing photo resizing are not numerical limits for incoming full-size images, thumbnails and audio.

**Suggested fix:** specify canonical zero/exact-multiple/final-segment cases, size equations and ciphertext ceilings. Define orphan handling before allocation/write, transfer scope and bounded range bookkeeping, and idempotent restart reconciliation from an accepted manifest. Give incoming decoder limits and failure behaviour. Test 0, 1, 65,535, 65,536 and 65,537 plaintext bytes, both size ceilings, manifest-before-first-chunk crashes, and oversized thumbnail/media declarations. Retain the standard STREAM implementation; no new cipher is needed.

### 10. Medium — the size evidence does not cover the stated worst case or replay claim

**Locations:** group encryption §§3.2, 3.9, §5 items 1/4; [size program](../../experiments/sender-key-sizes/src/main.rs).

The updated encoder really includes the inbox key. Its overhead is 16+8+4+24+16+4 = 72 bytes; the five-byte batch prefix is separate. The listed 453-byte open-session one-event pieces total 57,078 for 126 recipients, fitting 56 KiB, so one batch per remaining member is plausible at those measured sizes. The 2,102-byte new-session case totals 264,852, fitting five such batches.

But the same table reports **2,582 bytes** for a new session naming 16 events. For 126 recipients this is **325,332 bytes**, beyond five batches' 286,720-byte piece budget, requiring at least six batches per sender: **762 envelopes**, before fallback duplication/retries. Calling the one-event, five-batch row “worst case” understates a case the experiment itself measures. The documented 16-event open-session case already shows that event lists matter. Limits must be enforced from actual encoded bytes, not these sampled maxima.

The program also does not replay an identical first ciphertext, clear/recreate session state or test durable base-key records across restart. `Pair::send()` creates a fresh message and decrypts that new message once; repeated calls are different ciphertexts. Thus §§3.2/5's claim that this measurement confirmed replay refusal is not supported by this program. This does not establish a libsignal replay defect; it is an unsupported test claim. The experiment likewise counts the outer/container overhead rather than exercising a batch decoder.

**Suggested fix:** label every cost scenario with session state and event count; include the larger new-session case, fallback copies and retries where quoting recovery costs. Correct the replay evidence attribution or supply a separate, reproducible replay/persistence test against the pinned store behaviour. Preserve “largest seen, not a proven maximum”. My fresh Rust run failed during linking, so I do not independently reproduce the claimed libsignal byte measurements in this round.

### 11. Medium — the simulator still avoids terminal-hop split sends using recipient knowledge

**Locations:** [simulator source](../../experiments/copy-count-sim/src/CopyCountSim.java), `Run.offer()` around line 360; [README](../../experiments/copy-count-sim/README.md), hop rules; mesh §§1.3–1.4.

The previous last-copy defect is fixed: a carrier with one hop left now pays to transmit a last copy to a stranger, which drops it. The remaining condition is `newHops == 0 && !endpoint && (... || m.copies[a] > 1)`. A split holder with one hop left still skips the transmission to a stranger while transmitting to a recipient/member. The sender's OFFER contains no destination and WANT deliberately answers alike regardless of recipient status; it cannot know `endpoint` before sending the data. Zero-hop carrier storage refusal does not remove that preceding transmission or refund a sent allocation.

A focused harness against the unchanged source produced:

| --- | --- | --- | --- | --- |
| 1 | Stranger | 1 | 1 | 1 |
| 1 | Recipient | 1 | 1 | 1 |

The selected 44-row rerun matches the published CSV, so this is a model/wire mismatch rather than a failed reproduction. Its effect on full-run delivery or traffic has not been quantified here.

**Suggested fix:** decide the wire's terminal-hop split policy without a recipient oracle, then model that same send/debit/drop behaviour. If the holder refuses all terminal-hop splits, it must also refuse them to endpoints; if it sends them, it must charge stranger transmissions too. Rerun the comparisons after that decision. Do not repair it by revealing recipient status. Keep the current explicit disclaimers about absent bytes, eviction, reservations, loss, clocks and radio capacity.

**Locations:** mesh “What the limits really are”, §§1.3, 3.5, “Not covered” and tests; labels §§1–2, 6 and tests; group encryption §5 item 5.

## Direct transfer, STREAM and storage assessments

The direct transfer design now names an established Noise pattern rather than leaving cipher/nonces/directional keys to an implementer. The previous/current/next week selection can provide a shared PSK epoch when that secret exists. Smaller-identity initiation, both identities and the HELLO context are sensible binding requirements, and fresh Noise ephemeral keys/counters on a new link keep transport nonce state separate from file resume state. This is a composition to specify and review, not a new cryptographic construction approved here.

Before implementation review, write the exact initiator message carrying the week, canonical PSK-info/prologue bytes, bounded handshake dispatch and failure/restart states, and FILE_OFFER/CHUNK/ACK/DONE encodings. Bind file/range operations to an accepted immutable manifest; cap range lists, streams and work, and close/restart the channel according to the chosen Noise library's error rules. A DONE or FILE_ACK must not bypass complete file validation or become a group member's authenticated receipt. With 60 KiB of file bytes there is room for modest headers and a transport tag, but enforce the **65,535-byte complete Noise-message** ceiling, including its authentication tag. [Noise revision 34](https://noiseprotocol.org/noise_rev34.html) assigns framing/payload parsing to the application. No handshake or attachment implementation exists here to test.

StreamBE32 reserves five bytes of the AEAD nonce for its counter/final flag; a 24-byte XChaCha nonce therefore leaves the stated 19-byte stream nonce. That arithmetic is coherent. Manifest-authenticated ciphertext size/hash, exact segment count and final-flag authentication address truncation and cross-file substitution at the complete-file level. They do not eliminate staging-resource attacks, decoder risks or the boundary ambiguities in finding 9. No streaming crypto was designed or implemented during this review.

SQLCipher page encryption is an established way to hide database contents and per-chat indexes from a seized file without its key. It does not hide total database/WAL/folder sizes or access/change patterns, remove the need for byte admission, or protect an open compromised endpoint. [SQLCipher's design](https://www.zetetic.net/sqlcipher/design/) checks page MACs **when pages are read**; storage's test “a changed page fails to open the database” should not assume every page is verified merely by opening. Define deliberate integrity checks if whole-file validation is required. Version pins, raw-key settings, temporary-file policy, Android builds and carrier cost remain unverified. No comparative speed claim is justified.

Reservation-at-OFFER and busy-WANT do not require another primitive. Under the stated one-worker/atomic-store assumptions, fixed promises, unsent-only release and uncertain spending avoid the previous double-allocation contradiction. The cost is availability: abandoned transfers and crash-left reservations can consume copies without custody. It is correctly acknowledged. This review does not mistake a model without reservations for a test of those durability rules.
